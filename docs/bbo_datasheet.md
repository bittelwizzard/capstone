# BBO Capstone Data Sheet

## Motivation

This data set was created for the Black-Box Optimisation capstone project. It supports the search for high-scoring inputs to eight functions whose formulas are not provided.

Each input is a vector in the unit cube, with between two and eight dimensions. Each evaluation returns one numerical score. The initial arrays were supplied with the capstone materials; later results were returned after submitted queries.

The data set was created and maintained by the project author. No external funding is recorded.

## Composition

The data set contains 175 initial observations and 104 later query records from 13 rounds, for 279 input-output records total. Each round contains one query for each of the eight functions.

The initial data are stored in `function_1` through `function_8`:

- `initial_inputs.npy` contains the input arrays.
- `initial_outputs.npy` contains the matching output arrays.

The later data are stored in weekly folders:

- `inputs.txt` contains the submitted query points.
- `outputs.txt` contains the returned function values.

The final 13-round history is in [week 14/inputs.txt](../week%2014/inputs.txt) and [week 14/outputs.txt](../week%2014/outputs.txt). The round-13 submission is in [week 13/proposed_queries_round13.txt](../week%2013/proposed_queries_round13.txt).

The data are an adaptive sample, not a complete or even coverage of the input spaces. The function formulas, real-world meanings, true optimum values and untested candidate points are not available. No personal or sensitive information is included.

Exact repeated inputs occur in the history. Their outputs differ for Functions 2, 3 and 6. The cause is not documented, so these differences may reflect noisy or variable evaluations, or a record issue. There are not enough repeat measurements to estimate noise reliably.

### Sampling bias and gaps

Later queries were selected using earlier results, so the records are adaptively sampled rather than evenly distributed. Promising regions and some boundaries received more attention; other regions may be unobserved. The data do not represent a random sample of each function's full input space.

## Collection Process

The initial observations were provided for each function. Later observations were collected during the project rounds.

One query was submitted for each function in each round. Later queries were chosen using the results from earlier queries.

The query strategy evolved from expected-improvement search to Gaussian-process upper-confidence-bound search. Later versions adjusted candidate budgets by dimension and used clusters of observed inputs to guide local search. The final query generator returned to expected improvement, combining global candidates with local candidates around strong observed points and clusters.

The final proposals were generated by [scripts/propose_week13_queries.py](../scripts/propose_week13_queries.py). Fixed random seeds were used, candidates were kept inside the unit cube, and repeated training inputs were excluded from the new proposals.

The data are organised by project week. Exact collection dates were not recorded.

## Preprocessing and Cleaning

The initial NumPy files were used in their original numerical format.

The weekly text files were read and combined with the initial NumPy arrays before fitting the optimisation model. Candidate values were constrained to the unit cube and submitted to six decimal places.

No missing values were filled in, no labels were added and no unusual results were removed. Repeated inputs and their returned scores remain in the raw history.

The data were not divided into training, validation and test sets because this was a sequential optimisation task. Earlier results were used to choose later queries.

## Uses

The data set can be used to:

- Reproduce the BBO query process.
- Review the results from each project round.
- Study optimisation with a small query budget.
- Compare exploration and exploitation decisions.
- Study the effect of input dimensions on search coverage.

Key limitations: the data set does not establish a global optimum, does not evenly cover the functions and does not show that the functions are smooth. Repeated results also do not establish stable behaviour across the whole input space.

The data set is not suitable for safety-critical or production decisions. There are no repeated measurements and no guarantees about measurement accuracy.

## Distribution

The data set is stored in this project repository. The initial NumPy files total about 10 KB; the round logs are also small text files. No dataset file approaches the 50 MB threshold, so external hosting is not needed. It includes:

- Initial NumPy data.
- Weekly input and output files.
- Query-generation scripts.
- Project reflections.

No external API or hosted data service is used. Initial data came with the capstone project; later outputs came from the project evaluation process. No separate data licence is recorded.


## Maintenance

The project author maintains the data set and documentation.

For each new round, the input and output files should be stored together in a clearly named weekly folder. Existing raw files should not be overwritten.

Future updates should record:

- The date of the round.
- The software and package versions.
- The query-generation settings.
- The number of candidate points considered.
- Any changes to the optimisation strategy.
